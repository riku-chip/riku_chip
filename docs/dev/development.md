## Platform and prerequisites

**Linux x86_64** is the supported platform. Windows is not supported (the gdstk C++ engine does not link with MSVC).

You need:

- Rust **stable** (`rustup default stable`).
- A C++ toolchain (`build-essential` on Debian/Ubuntu), `pkg-config`, **zlib** (`zlib1g-dev`) and **qhull** (`libqhull-dev`), for the gdstk engine.
- For the desktop viewer (feature `gui`): `libxkbcommon-dev`, `libwayland-dev` and `libgl1-mesa-dev`.

On Debian or Ubuntu:

```bash
sudo apt-get install -y build-essential pkg-config zlib1g-dev libqhull-dev \
  libxkbcommon-dev libwayland-dev libgl1-mesa-dev
```

Verification scripts and demo generators additionally need EDA tools (KLayout, Magic, Netgen, Xschem, ngspice) and PDKs. One convenient option is the [iic-osic-tools](https://github.com/iic-jku/iic-osic-tools) container, which ships all of them; it is not required.

## Building

```bash
git clone --recurse-submodules https://github.com/riku-chip/riku_chip
cd riku_chip
cargo build --release            # target/release/riku: CLI, shell and viewer
```

The repository is a Cargo workspace (`viewer-core`, `riku-kernel`, `riku-mod-layout`, `riku`) with one `Cargo.lock` and one `target/`. The engines in `external/` are Git submodules used as path dependencies. After every `git pull`, run:

```bash
git submodule update --init --recursive
```

### Feature flags

Features of the `riku` crate (all enabled by default):

| Feature | What it adds |
|---|---|
| `xschem` | Xschem schematics (`.sch`, `.sym`), through `external/xschem-viewer-rust`. |
| `layout` | GDSII, OASIS and Magic layouts, through `riku-mod-layout` and `external/gdstk`. |
| `spice` | ngspice `.raw` waveform diffs (std only, no extra dependencies). |
| `gui` | The egui desktop viewer (`riku open`, `riku gui`). Without it you get a terminal-only binary. |

`riku lvs` is compiled only when both `xschem` and `layout` are enabled.

```bash
cargo build --release -p riku --no-default-features                      # terminal only, no format modules
cargo build --release -p riku --no-default-features --features layout     # layouts only, no viewer
cargo build --release -p riku --no-default-features --features xschem,layout,spice   # all formats, no viewer
```

`viewer-core` has one feature, `parallel`, which builds the scene index with `rayon`; `gui` turns it on.

The workspace `Cargo.toml` optimizes a few crates even in debug builds (the SVG/PNG rasterizer and the Xschem parser), so `cargo run` stays usable on real designs.

## Tests

```bash
cargo test --workspace            # everything (CI runs it with RUSTFLAGS="-D warnings")
cargo test -p riku                # CLI, analysis, modules, LVS, viewer logic
cargo test -p riku-mod-layout     # layout diff, cache, layer styles, devices, nets, scene
cargo test -p viewer-core         # viewer contract and spatial index
cargo test -p riku-kernel         # change types and registry
```

Integration tests of `riku` are in `riku/tests/`: `basic.rs`, `gds_e2e.rs`, `mag_e2e.rs` and `stress.rs`. They create temporary Git repositories, so Git needs a user identity (`git config --global user.name/user.email`).

A few tests are `#[ignore]` because they need large files outside the repository (for example `RIKU_BIG_A`/`RIKU_BIG_B` pointing to two versions of a large GDS). Run them explicitly with `cargo test -- --ignored <name>`.

The Magic reader lives in the `gdstk-rs` submodule and has its own tests:

```bash
cd external/gdstk/rust
cargo test --test magic           # pdk_corpus and klayout_testdata are ignored: they need $MAG_CORPUS / $KLAYOUT_TESTDATA
```

### Fixtures

- Layout fixtures in `riku-mod-layout/tests/fixtures/` are generated by the Python scripts in that directory (`gen_*.py`, using the `gdstk` and `klayout` Python packages). Commit both the script change and the regenerated files.
- Magic fixtures are written inline in the tests.
- `examples/SH/op_sim.sch` and `examples/GDS/sram_16x8_sky130.gds` are used by the `riku` integration tests.
- Compiled PDK tables are regenerated with `tools/palettes/` when a PDK changes:

```bash
python3 tools/palettes/gen_palettes.py      "$PDK_ROOT"   # riku-mod-layout/src/palette_generated.rs (from the .lyp files)
python3 tools/palettes/gen_devices.py       "$PDK_ROOT"   # riku-mod-layout/src/devices/devices_generated.rs (from the Magic .tech files)
python3 tools/palettes/gen_magic_layers.py  "$PDK_ROOT"   # riku-mod-layout/src/magic_layers_generated.rs (Magic layer planes and contacts)
```

When measuring `log`, `status` or the viewer, use a repository on a local disk: network or virtualized mounts distort the timings.

## Verification

The scripts in `tools/verify/` check Riku against the reference tools: that it reads layouts exactly like KLayout, that its transistors and nets match PDK netlists and Magic (through Netgen), that its schematic netlists match Xschem's, and that the viewer behaves under scripted input. They do **not** run in CI because they need external tools and PDKs. Run them by hand before changing the readers, rendering, labels, the diff, device or net extraction.

Requirements, depending on the script:

| Tool | Used by |
|---|---|
| KLayout Python module **0.30.12 or newer** (`pip install klayout==0.30.12`; 0.30.4 and older ignore Magic `magscale`) | `compare.sh`, `mag/`, `devices/klayout_gates.py`, `klayout_snapshot.py` |
| Magic | `nets/magic_vs_riku.sh`, `nets/chip_vs_magic.sh` |
| Netgen | `nets/`, `netlist/` |
| Xschem | `netlist/compare_xschem.sh` |
| PDKs (SKY130, GF180MCU, IHP SG13G2) under `$PDK_ROOT` | all PDK-based checks |
| An X server, `xwininfo`, `xwd`, Python `Pillow` | `gui/` |

Scripts read `PDK_ROOT` (they fall back to `/foss/pdks`, the iic-osic-tools location), write to `$OUT` (default `$TMPDIR/riku-verify…`) and look for compiled examples under `$CARGO_TARGET_DIR` (default `target/`).

### Geometry, labels and XOR

| Script | What it checks |
|---|---|
| `compare.sh` | Builds the `verify_dump` example, dumps each library with Riku and with KLayout (`klayout_dump.py`), and diffs the two texts. Exits 1 on any difference. |

```bash
tools/verify/compare.sh                           # SKY130, GF180 and IHP standard-cell libraries
tools/verify/compare.sh my_chip.gds other.oas     # your own libraries (GDSII or OASIS)
tools/verify/compare.sh --xor a.gds b.gds CELL    # added/removed area per layer
```

For each top cell the dump contains the bounding box (or `BBOX empty`), the polygon count and area per layer (µm², overlaps not merged), and every label in the hierarchy with its position in the root cell.

### Magic

```bash
tools/verify/mag/compare_mag.sh                          # bundled SKY130 and GF180 hierarchies
tools/verify/mag/compare_mag.sh top.mag 0.01 DIR...      # your own: lambda in µm and where to find sub-cells
```

`compare_mag.sh` reads `.mag` hierarchies with `gdstk-rs` (the `mag_area` example in `external/gdstk/rust`) and with KLayout (`klayout_mag_area.py`), flattened and unmerged, and requires the same polygon count and total area per layer. Layers Riku drops on purpose (`checkpaint`, `error_*`, …) do not count. Set `KLAYOUT_PY` to the Python that has KLayout 0.30.12+.

`mag/mag_bench.sh` measures the diff of a real Magic hierarchy (time, memory, number of changes); set `RIKU` to the binary to measure.

### Transistors

```bash
cargo build --release -p riku-mod-layout --example devices
tools/verify/devices/compare_stdcells.sh "${CARGO_TARGET_DIR:-target}/release/examples/devices"
```

Compares the transistors Riku recognizes (model, W and L of each finger) against the reference netlist of every standard cell of each installed PDK. The few known mismatches are listed in the script; in those cells the PDK netlist does not match its own layout, and `klayout_gates.py <gds> <cell> <diffusion> <poly>` (KLayout's MOS extractor) agrees with Riku.

### Nets

```bash
cargo build --release -p riku-mod-layout --example nets
tools/verify/nets/compare_stdcells.sh "${CARGO_TARGET_DIR:-target}/release/examples/nets"
tools/verify/nets/magic_vs_riku.sh sky130A layout.gds CELL...      # Magic as a second oracle
```

`compare_stdcells.sh` compares Riku's extracted netlist (nets, transistors, resistors) with each standard cell's reference netlist using **Netgen** and the PDK's `setup.tcl`, i.e. a full topological comparison. `magic_vs_riku.sh` extracts the same cells with Magic and compares them with Riku; when Magic agrees with Riku, the PDK reference is the one that does not reflect the layout. Known exceptions are listed in the script.

Hierarchical extraction is checked against flat extraction, and a full chip against Magic:

```bash
cargo build --release -p riku-mod-layout --example hier_check
riku demo --dir ~/riku-demos                       # optional: lets hier.sh also check the demos
tools/verify/nets/hier.sh ~/riku-demos             # every line must say "IGUALES" (equal)
tools/verify/nets/chip_vs_magic.sh ~/riku-demos/chip   # slow: Magic + Netgen on the whole macro
```

`hier_check <layout> [cell]` extracts a cell both ways and compares transistors, nets, names, pins and substrate. Its environment variables are listed under [Development environment variables](#development-environment-variables).

### Schematic netlists

```bash
cargo build --manifest-path external/xschem-viewer-rust/Cargo.toml --example spice
tools/verify/netlist/compare_xschem.sh [binary] [max per PDK]
```

Compares the schematic netlist Riku writes in LVS mode (the `xschem-viewer-rust` netlister) against Xschem's own netlist of each PDK example schematic, with Netgen. A schematic counts as equivalent when Netgen gives the same verdict for Riku-vs-Xschem as for Xschem-vs-itself.

### Visual comparison

```bash
python3 tools/verify/klayout_snapshot.py \
  "$PDK_ROOT/sky130A/libs.ref/sky130_fd_sc_hd/gds/sky130_fd_sc_hd.gds" \
  "$PDK_ROOT/sky130A/libs.tech/klayout/tech/sky130A.lyp" \
  klayout_inv1.png sky130_fd_sc_hd__inv_1 800 600
```

Renders a cell with KLayout and the PDK's official palette, to compare side by side with `riku gui <file> --cell <cell>`.

### Scripted viewer tests

`tools/verify/gui/xt.py` drives the viewer window through XTest (clicks, drags, wheel, keys) and captures it with `xwd`:

```bash
env -u WAYLAND_DISPLAY cargo run --release -- gui file.gds &     # force X11/XWayland so the window can be captured
W=$(xwininfo -root -tree | grep 'riku-gui")' | awk '{print $1}')
python3 tools/verify/gui/xt.py $W raise
python3 tools/verify/gui/xt.py $W click 120 80
python3 tools/verify/gui/xt.py $W drag 600 400 500 350 300       # 300 ms drag
python3 tools/verify/gui/xt.py $W keytap f                       # "fit" shortcut
python3 tools/verify/gui/xt.py $W shot riku.png
```

`gui/xwd2png.py` converts a standalone `xwd` capture to PNG.

## Profiling

`RIKU_PROFILE=1` prints stage timings of the layout diff and net extraction, and per-frame paint times in the viewer.

The examples in `riku-mod-layout/examples/` measure individual stages. Build them in release mode and run them on a local disk:

| Example | Usage | Measures |
|---|---|---|
| `profile_diff` | `profile_diff a.gds b.gds [seconds_per_stage]` | Time and memory of each diff stage (read, fingerprints, flatten, XOR). `SKIP_FP=1`, `PRINTS=1`, `CANON=1` enable diagnostics. |
| `profile_view` | `profile_view layout.gds` | Time to build the viewer scene and index, without a window. |
| `profile_prints` | `profile_prints layout.gds [cell] [threads]` | Chunked fingerprinting: partitioning, timings, memory, thread scaling. |
| `profile_xor` | `profile_xor a.gds b.gds CELL LAYER DATATYPE` | One layer's XOR, whole vs. split into tiles. `SKIP_WHOLE=1` skips the whole XOR when it takes minutes. |
| `hier_check` | `hier_check layout [cell]` | Hierarchical vs. flat net extraction (see [Verification](#verification)). |
| `nets`, `devices` | `nets [--unit u] layout [cell...]` | Extracted netlist or transistor list per cell, as used by the verification scripts. |
| `verify_dump` | `verify_dump cells layout` / `verify_dump xor a b cell` | The dump compared by `compare.sh`. |
| `lvs_probe` | `lvs_probe layout cell name...` | What the LVS view would locate in the layout for Netgen device and net names. |

```bash
cargo build --release -p riku-mod-layout --example profile_diff
"${CARGO_TARGET_DIR:-target}/release/examples/profile_diff" before.gds after.gds
```

Compare the minimum of several runs, with the disk cache off (`RIKU_NO_CACHE=1`), against the previous binary.

## Development environment variables

These are for development and diagnosis; user-facing variables (`RIKU_LANG`, `RIKU_JOBS`, `RIKU_CACHE_DIR`, `RIKU_NO_CACHE`, `PDK_ROOT`, …) are documented in [configuration.md](../configuration.md).

| Variable | Read by | Effect |
|---|---|---|
| `RIKU_PROFILE` | `riku-mod-layout`, viewer | Any value: print stage timings (diff, net extraction) and per-frame paint times. |
| `RIKU_LOD_PX` | viewer | Block size in pixels of the coverage pyramid: geometry smaller than this on screen is painted as per-layer coverage instead of individual shapes (default `1`). |
| `RIKU_HIER_INLINE` | net extraction | Sub-cells with fewer flattened polygons than this are inlined into their parent (default `256`; `0` disables inlining). Part of the cell key, so changing it invalidates cached extractions. |
| `RIKU_NETS_MEM_MB` | net extraction | In-memory cap for extracted cells, in MB (default `512`; `0` disables the memory cache). |
| `RIKU_FULL_NETS` | layout diff | `1`: compare nets of cells above 2 million flattened polygons even if they were never extracted (slow the first time). |
| `RIKU_FLAT_NETS` | layout diff | `1`: use flat extraction for the net and device diff instead of per-cell extraction (for comparison). |
| `RIKU_LVS_KEEP` | `riku lvs` | Directory where the netlists and the Netgen report of each run are kept. |
| `RIKU_BIG_A`, `RIKU_BIG_B` | ignored tests | Paths to two versions of a large GDS for the performance tests. |
| `RIKU_BENCH_N` | ignored LVS test | Number of transistors in the manual-LVS benchmark (default `2000`). |
| `HIER_NO_FLAT` | `hier_check` | Skip the flat extraction (for cells too large to flatten). |
| `HIER_SPICE` | `hier_check` | Write the hierarchical netlist as SPICE to this file. |
| `HIER_UNIT` | `hier_check` | W/L suffix in the SPICE written by `HIER_SPICE`. |
| `HIER_NET` | `hier_check` | Show which child nets reach the root net with this name. |
| `HIER_WHERE` | `hier_check` | `x,y` in µm: show the path through the hierarchy to that transistor. |
| `HIER_TWICE` | `hier_check` | Extract a second time to measure the memoized run. |

## Demos

`riku demo` clones Git bundles embedded in the executable (`examples/demos/*.bundle`, loaded by `riku/src/cli/demo.rs`). Each bundle is produced by a script in `tools/demos/`:

```bash
python3 tools/demos/ota.py      examples/demos/ota.bundle        # Xschem, ngspice and KLayout
python3 tools/demos/sram.py     examples/demos/sram.bundle       # KLayout
python3 tools/demos/inversor.py examples/demos/inversor.bundle   # Magic, Netgen; uses RIKU and NETS
python3 tools/demos/chip.py     examples/demos/chip.bundle       # KLayout; GDS taken from the PDK
```

- **Deterministic.** `tools/demos/common.py` fixes the author (`Riku Demo <demo@riku.invalid>`) and commit dates, so the same inputs and tool versions produce the same bundle byte for byte. `chip.py` writes the GDS without timestamps. Only commit a regenerated bundle when its content is meant to change.
- **Environment.** The scripts expect the EDA tools on `PATH` (they prepend `/foss/tools/bin`, the iic-osic-tools location) and the PDKs under `$PDK_ROOT`.
- **Self-checking.** `inversor.py` edits the `.mag` files as text (stretching like Magic's `stretch` to change W and L without moving external connections) and, before writing the bundle, checks every commit: the LVS verdicts of `riku log --lvs` against an expected table, that each `riku show` says what the demo README promises, and that Riku's extracted netlist matches Magic's (`extract all` + Netgen). If anything fails, no bundle is written. Point `RIKU` at the `riku` binary and `NETS` at the `nets` example (defaults are under `$CARGO_TARGET_DIR/debug`).
- **Licenses.** `ota` comes from the CACE `ota-5t` example and `inversor` from the iic-osic-tools `demo_sky130A`, both Apache-2.0 (their `LICENSE` files are in `tools/demos/ota/` and `tools/demos/inversor/`). `chip` is `sky130_sram_1kbyte_1rw1r_32x256_8` from VLSIDA's `sky130_sram_macros` (Apache-2.0). `sram` is built from `examples/GDS/sram_16x8_sky130.gds` (OpenRAM, BSD-3-Clause; SkyWater cells, Apache-2.0). Each demo repository carries its license and attribution in its README.

## Formatting and linting

Formatting is configured in `rustfmt.toml` at the root (`max_width = 130`, `use_small_heuristics = "Max"`). Format **per package**, never with `--all`, which would also reformat the submodules in `external/`:

```bash
cargo fmt -p viewer-core -p riku-kernel -p riku-mod-layout -p riku
cargo clippy --workspace --all-targets --locked
```

The commit that reformatted the whole codebase is listed in `.git-blame-ignore-revs`. GitHub skips it automatically; to skip it locally:

```bash
git config blame.ignoreRevsFile .git-blame-ignore-revs
```

## Continuous integration

`.github/workflows/ci.yml` runs on pushes to `main`, on pull requests, manually, and as the first stage of a release. Jobs:

| Job | What it runs | Blocking |
|---|---|---|
| `fmt` | `cargo fmt --check -p viewer-core -p riku-kernel -p riku-mod-layout -p riku` | Yes |
| `clippy` | `cargo clippy --workspace --all-targets --locked` | No (`continue-on-error`; read the warnings in the log) |
| `test` | `cargo test --workspace --locked` with `RUSTFLAGS=-D warnings`, then the feature builds below, then a check that `riku-kernel` does not depend on `riku-mod-layout`, `xschem-viewer` or `gdstk-rs` (`cargo tree`) | Yes |
| `xschem-compat` | `cargo check --features viewer-core-compat` in `external/xschem-viewer-rust`, against the current `viewer-core` | Yes |

Feature builds in the `test` job (besides the default set used by the tests):

- `-p riku --no-default-features`
- `-p riku --no-default-features --features layout`
- `-p riku --no-default-features --features xschem`
- `-p riku --no-default-features --features layout,gui`

Other combinations (for example `spice` alone, or `xschem,gui`) are not built in CI. All jobs run on `ubuntu-24.04` and build with `--locked`, so `Cargo.lock` must be committed with any dependency change.

## Releasing

`.github/workflows/release.yml` runs on every pushed tag matching `v*`:

1. Runs the whole CI workflow on the tagged commit. If it fails, nothing is built or published.
2. On `ubuntu-22.04` (glibc 2.35), builds `riku` in release mode with gdstk and qhull linked statically (`GDSTK_STATIC=1`, qhull 8.0.2 built from source), so the binary links only against glibc.
3. Fails if `ldd` shows any dependency outside the allowed glibc set.
4. Smoke tests: `--version`, a GDS diff in JSON (`riku-diff/v2`), a Magic sub-cell change seen from the top cell, and `riku gui` failing cleanly without a display.
5. Packages `riku-<version>-linux-x86_64.tar.gz` (binary, `install.sh`, desktop entry, icon, README, LICENSE), `riku_<version>-1_amd64.deb` (via `cargo-deb`) and `SHA256SUMS`. `<version>` is taken from `riku --version`, i.e. from `riku/Cargo.toml`.
6. Uploads them as workflow artifacts and creates the GitHub release titled `Riku <tag>` with those three assets and notes generated by GitHub (`gh release create --generate-notes`).

To cut a release:

```bash
# 1. bump `version` in riku/Cargo.toml, update Cargo.lock (cargo build) and CHANGELOG.md
git commit -am "release: riku X.Y.Z"
git tag -a vX.Y.Z -m "Riku X.Y.Z"
git push origin main vX.Y.Z
```

The workflow does not check that the tag matches the crate version; make sure they agree. After it finishes, edit the generated notes on GitHub if needed, listing incompatible changes first. **Actions → Release → Run workflow** (manual dispatch) runs the full build and leaves the packages as workflow artifacts without publishing a release.

## Translations

All user-visible text of the CLI and the viewer lives in `riku/locales/`: `en.yml` (the default and the fallback) and `es.yml`. Files are embedded at compile time; the list of available languages (viewer menu, `RIKU_LANG`) comes from the files present.

To add a language:

1. Copy `riku/locales/en.yml` to `riku/locales/<code>.yml` (for example `pt.yml`).
2. Translate the values. Never change the keys or the `%{…}` placeholders.
3. Set `lang.name` to the language's own name (for example `"Português"`).
4. Run `cargo test -p riku i18n`. The tests report keys that are missing or extra, and placeholders that do not match English.

To add a new string in code, use `tr!("section.key")` (with `name = value` arguments for placeholders) and add the key to **every** `.yml` file.

> [!NOTE]
> Messages produced inside `riku-mod-layout` and `riku-kernel` do not go through `tr!` yet, so they are not translated. Some layout warnings are still hard-coded in Spanish.
